# Yoke — тестові сценарії за персонами

Два наскрізні сценарії від першого відкриття до повторного запуску, прив'язані до
реальних екранів (`src/serve.py`) і гейтів. Кожен крок: **дія → що має статись**.
Позначки: ✅ pass-критерій · ⚠️ гейт/межовий кейс · 🔌 потребує реального провайдера/мережі.

> Мова — українська (внутрішній QA-артефакт). Якщо піде в публічний репо — перекласти.

---

## Персона 1 — Активний пошукач (Anna)

**Профіль.** Шукає активно, подає по кілька заявок на день, готова лейбити багато,
тейлорить CV під кожну вакансію, дивиться на воронку (відгуки/співбесіди), хоче, щоб
скоринг підлаштувався під її реальні рішення. Цінність для неї — **flywheel + funnel**.

### A. Перше відкриття (cold start)
1. `./yoke` → відкривається борд на http://localhost:8765/.
   ✅ Борд порожній → картка *"Board is empty. Set a provider in Settings and your CV in Profile, then hit ▶ Run now."*
2. Клік **Settings**.
   - Provider: вибрати (`claude_code` дефолт = підписка Claude, без ключа в інтерактиві / `openrouter`+ключ / `ollama` локально).
   - Sources: лишити дефолтні (jobspy off), у *Target companies* додати 2–3 рядки `name,ats,slug` (напр. `Mistral,lever,mistral`).
   - **Save settings**. ✅ toast *"Settings saved."*
3. Клік **Profile**.
   - Name, Headline, Output language, **Comp floor** (напр. 0 для активного — широкий захват).
   - *Scoring profile (prompt)*: lane, диференціатори, seniority, мови, geo, comp.
   - *Resume text*: вставити CV (йде в скоринг). **Save profile**. ✅ toast.
4. Клік **▶ Run now**. ✅ toast *"Run started in the background — refresh in a minute."*
   🔌 Тут реально працюють скрапери + LLM. Перевірити консоль на парс-фейли.

### B. Тріаж борду (основний цикл)
5. Через ~хв оновити борд (auto-refresh 60s). ✅ З'являються ролі, **tier A зверху**, далі B; сортування за (tier, fit↓).
6. Прочитати рядок: `tier-бейдж · fit · label · geo · title·company · comp · ✓Apply`.
   ⚠️ Після фіксу A: роль з `fit≥85` але `geo≠remote` показує **"🟢 Strong"** (демоут), а не "Top candidate"; verify-стан несе geo-колонка поруч. Справжній "Top candidate" — тільки remote-confirmed.
   ⚠️ Після свіжого run: оцінений comp має суфікс **"est"** (`~$6-9k est`); зіскрейплений — без нього.
7. Клік на роль → розгортається `note` (чому такий скор) + блок reject (reason-select + comment).
8. Перспективна роль → **✓ Apply** → сторінка `/apply`:
   - Картка ролі (fit/label/geo/comp + *open posting →*).
   - **Gap vs your CV**: match-band + matched/missing скіли (детермінований, без моделі).
   - Textarea з CV (прозаповнена base CV) — **відредагувати під роль**.
   - Notes (кут cover-letter, реферал).
   - ⚠️ Нічого не пишеться до **✓ Confirm — I applied**. Apply — це *флоу*, не 1-клік-зникнення (рішення 6518f299).
   - (опц.) у терміналі `yoke cover <role_key>` — чернетка листа, нічого не авто-надсилається.
   ✅ Після Confirm роль зникає з борду, з'являється в **Applied**; CV-снапшот **незмінний**.
9. Непідхожі ролі → **✗ Reject** з reason. ✅ Інстант, без проміжного кроку.

### C. Воронка та flywheel
10. Клік **Applied** → таблиця заявок + аналітика: `total · response rate · interview rate · offers` + розклад по статусах.
    - Для кожної заявки змінити статус (`applied→screening→interview→offer/rejected`) + note. **Save**.
    ✅ Воронка перераховується.
11. Набрати **≥5 applied AND ≥5 rejected** (обидва класи).
    ⚠️ До цього порогу кнопка **⚙ Improve (locked)** — tooltip показує `n_pos+/n_neg−`.
12. Коли розблоковано → **⚙ Improve** → сторінка refit:
    - `balanced accuracy: before → after`, таблиця змінених ваг.
    - Якщо точність зросла → **Apply new weights**. ✅ Ваги зберігаються в store.
    ⚠️ Тюнер рухає **тільки ваги**, не cutlines (THRESHOLD=55, TIER_A=70 фіксовані).
    ⚠️ `interested` НЕ рахується як позитив тюнера — тільки `applied` vs `rejected`.

### D. Повторне відкриття (наступний день)
13. `./yoke` знову. ✅ Очікувати:
    - Борд містить **нові** ролі; вже оброблені (applied/rejected) не повертаються (дедуп за role_key).
    - Мертві посилання відсіяні (URL-liveness prune: 404/410 → drop; 5xx/transient → лишається).
    - **Applied** зберігся; **ваги** після Improve зберіглися.
    - Скор нових ролей рахується вже **підлаштованими** вагами.
14. Повторити тріаж. ✅ Субʼєктивно: топ борду ближчий до її смаку, ніж першого дня.

**Pass-критерій Anna:** проходить cold-start → run → тріаж → apply-flow → набирає лейбли →
Improve дає Δ точності ≥ 0 → воронка рахує rates → повторний запуск не дублює рішення.

## Персона 2 — Пасивний пошукач (Pavlo)

**Профіль.** Має роботу, дивиться ринок «одним оком». Мінімум зусиль, не хоче шуму,
хоче бачити **тільки топ remote-confirmed** ролі вище своєї comp-планки. Подає рідко,
частіше «закладає» цікаве. Цінність для нього — **тихий фільтр + cron**, не flywheel.

### A. Перше відкриття (мінімальна настройка)
1. `./yoke` → борд порожній.
2. **Settings** → provider: `ollama`/`lmstudio` (локально, без ключа) або `claude_code`. Sources дефолтні. **Save**.
3. **Profile** → CV + prompt; **Comp floor** виставити реально (напр. 10000 — нижче ~$10k net не варіант).
   ⚠️ Ролі з comp нижче планки → tier C → **не потрапляють на борд** взагалі.
4. **▶ Run now**, зачекати. 🔌

### B. Тихий перегляд (ключова відмінність від Anna)
5. Борд заповнився → **одразу клік «remote-confirmed only (N) →»**.
   ✅ Список згортається до geo=remote ролей (у поточних даних: 52 → 9). `⚠️ verify` не протікає.
   ✅ Якщо remote-confirmed = 0 → картка *"No geo-confirmed remote roles… N roles need a geo check"* + лінк назад (не «борд порожній»).
6. Переглянути лише цей короткий список. Решту (verify) — ігнорувати, гейт уже відсортував.
   ⚠️ Це гібрид B: широкий захват лишається в БД, але дефолт-увага — на підтверджене.
7. Цікаве, але не зараз → клік **☆** у рядку.
   ✅ Інстант (як reject, без флоу). Роль зникає з борду, з'являється у вкладці **★ Interested**.
   ⚠️ Зірочка — закладка, НЕ позитив тюнера; tuner її ігнорує.
8. Клік **★ Interested** → короткий shortlist збережених ролей.
   ✅ Кожну можна **✓ Apply** (лог-флоу) або **✗ Reject** прямо звідти. Зірочки тут нема (вже збережено).
   ✅ Shortlist переживає `run` (save() чистить лише live-ролі).

### C. Автоматизація (поставив і забув)
9. Клік **Schedule (cron)** → вибрати пресет (дефолт «twice daily») або custom hours → **Schedule**.
   ✅ toast *"Scheduled: daily at minute M of hours H."*
   ⚠️ Cron headless → потребує токен/ключ у Settings (або локальна Ollama). macOS: Full Disk Access для `/usr/sbin/cron`.
10. Закрити апку. Cron ганяє collect+score у фоні двічі на день.

### D. Повторне відкриття (за кілька днів)
11. `./yoke`. ✅ Очікувати:
    - Борд уже оновлений cron-ом (без ручного Run).
    - Клік «remote-confirmed only» → нові підтверджені ролі зверху.
    - **★ Interested** shortlist на місці (зірочки пережили run-и).
    - Мертві лінки відсіяні; стара історія не дублюється.
    - **Improve лишається locked** — і це ОК: пасивний юзер не лейбить, покладається на дефолт-ваги + geo-гейт.
12. Раз на N відкриттів натрапляє на справді підхожу (на борді чи в shortlist) → той самий **✓ Apply** флоу → CV-снапшот → Applied.

**Pass-критерій Pavlo:** мінімальна настройка → один Run → remote-only фільтр дає короткий чистий
список → cron планується → повторний запуск показує свіже без ручної роботи → tuner мовчить без докору.

## Зведена матриця гейтів (перевірити обома персонами)

| Гейт / поведінка | Очікування | Де |
|---|---|---|
| Run без провайдера | блок + *"Pick an AI provider in Settings"* | serve.py:129 |
| geo не remote | label демоут до «Strong», tier ≤ B, не «Top candidate»; verify несе geo-колонка | analyze.py (фікс A) |
| comp оцінено моделлю | суфікс «est» (тільки свіжий run) | analyze.py (фікс C) |
| comp нижче планки | tier C, поза бордом, маркер ⛔<floor | analyze.py |
| Improve | locked до ≥5 applied AND ≥5 rejected | serve.py / tune.py |
| ☆ star / `interested` | інстант-закладка → ★ Interested, НЕ позитив тюнера, переживає run; ★ повертає на борд | serve.py / store.py |
| Apply | флоу review→confirm, CV-снапшот незмінний | serve.py /apply |
| Reject | інстант | serve.py /mark |
| Повторний запуск | дедуп рішень + URL-liveness prune | store/board |
